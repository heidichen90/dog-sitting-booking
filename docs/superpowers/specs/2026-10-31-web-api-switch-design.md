# Website → API switch-over design

**Date:** 2026-10-31
**Status:** approved 2026-10-31
**Builds on:**
- `2026-10-29-backend-schema-design.md` (V1 schema)
- `2026-10-30-booking-api-design.md` (booking API, merged in PR #2)

**Branch:** `feat/web-api`

## Goal

Make the `web/` booking form, confirmation and history use the booking API instead of browser storage, running locally against `api/` and Postgres.app.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Where it runs | Locally only (website + API + Postgres.app). The live Vercel site stays on today's browser-storage version | The API isn't hosted yet, and the owner uses the live site for real bookings |
| Merging | `feat/web-api` is **not merged to `main` until the API is hosted**. Vercel auto-deploys `main` | Merging earlier would break the live site |
| API path prefix | All endpoints move under `/api` (`/api/clients`, `/api/bookings`, …) by changing the two controllers' `@RequestMapping` | One Vite proxy rule now, one Vercel rewrite later; no clash with website routes. Health check and `/v3/api-docs` stay put |
| Dev connection | Vite proxies `/api` to `http://localhost:8080`; the website calls relative paths | Same origin in the browser, so no CORS needed yet; the same code works behind a Vercel rewrite later |
| Types | `openapi-typescript` (dev-only) generates `web/src/api/schema.d.ts` from `/v3/api-docs`; the file is committed | Types match the API; building the site doesn't need the API running |
| API client | A small hand-written typed fetch helper, no runtime library | Four calls; keeps the bundle and dependency list small |
| Client and dog input | Search-as-you-type pickers fed by `GET /api/clients`; typing a new name creates a new client (with optional phone) or dog | No duplicate clients from typos; matches the API's `{id}` or new-details request shape |
| Notes | One notes box per booking, moved next to owner and dog | The API stores notes per booking |
| History | One card per booking with its days listed inside; **Delete becomes Cancel** (with a confirm prompt); cancelled bookings stay listed, greyed out with a "Cancelled" chip | Matches the API; nothing is hard-deleted |
| WhatsApp | Unchanged: opens WhatsApp with the message filled in; you pick the chat | Direct-to-client chat is deferred to the WhatsApp phase |
| Tests | Vitest + Testing Library + MSW (fake API), all dev-only; `npm test` added to `web.yml` CI | `web/` has no tests today; CLAUDE.md requires them |

### New dependencies (approved)

All are dev-only:
- `openapi-typescript`
- `vitest`
- `@testing-library/react`
- `@testing-library/user-event`
- `jsdom`
- `msw`

Exact versions are chosen in the plan and must work with Vite 8, React 19 and TypeScript 5.9.3 (pinned).

## Part 1: API changes (first)

Back-end changes that the website depends on. No schema change.

### 1a. `/api` prefix

- `ClientController` becomes `@RequestMapping("/api/clients")`, and `BookingController` becomes `@RequestMapping("/api/bookings")`.
- The `POST /api/bookings` `Location` header becomes `/api/bookings/{id}`.
- All MockMvc tests, `OpenApiTest`, the booking API spec's contract table and `api/CLAUDE.md` are updated to the new paths.
- `/actuator/health` and `/v3/api-docs` are unchanged.

### 1b. Precise OpenAPI output

This uses springdoc annotations and needs no new dependency. These are the items recorded in the booking API spec's "Future to-dos":

- **Required and nullable fields:** every response field is required. `notes`, `paidAt`, `phone`, `dropOffTime` and `pickUpTime` are additionally nullable.
- **Fixed value lists:** `status` is an enum (`confirmed`, `cancelled`), and `service` is an enum (`day_care`, `boarding`).
- **Create response:** `POST /api/bookings` is documented as `201` with a `Location` header.
- **Error responses:** the 400, 404 and 409 ProblemDetail shapes are documented, including `errors[]` (`field`, `message`) and `existingClient` (`id`, `name`).
- **Request schema fixes:**
  - `stays` shows `minItems: 1`.
  - Times are documented as `HH:mm` strings.
- **Readable operation ids:** `listClients`, `createBooking`, `listBookings`, `getBooking`, `cancelBooking`.
- **Responses:** declared as `application/json`.
- **Test:** `OpenApiTest` asserts the required, nullable, enum, 201 and operation-id points above.

## Part 2: Website

### Layout

```
web/src/
  api/
    schema.d.ts        generated by `npm run gen:api`; committed
    client.ts          typed fetch helper + ApiError
  phone.ts             UK phone input → E.164
```

The existing components (`BookingForm`, `BookingEntry`, `Confirmation`, `BookingHistory`) are reworked in place. `storage.ts` is deleted. In `types.ts`:
- The old `Booking` type is replaced by the generated API types.
- `BookingDraft` stays, adjusted as below.

### Scripts and config

- **`npm run gen:api`:** runs `openapi-typescript http://localhost:8080/v3/api-docs -o src/api/schema.d.ts`. The API must be running.
- **`npm test`:** runs `vitest run`.
- **`vite.config.ts`:** `server.proxy: { '/api/': 'http://localhost:8080' }` (trailing slash, so routes like `/apiary` aren't proxied), plus the Vitest config (`environment: 'jsdom'` and a setup file that starts MSW).
- **CI:** `.github/workflows/web.yml` gains `npm test`.

### `api/client.ts`

Functions:
- `listClients()`
- `createBooking(request)`
- `listBookings()`
- `cancelBooking(id)`

Each is typed from `schema.d.ts` and calls a relative `/api/...` URL.

A non-2xx response throws an `ApiError` carrying:
- `status`
- `title`
- `detail`
- `fieldErrors`: an array of `{ field, message }`, empty if none
- `existingClient`: `{ id, name }` or `null`

A network failure throws `ApiError` with status 0.

### App data flow

- **On load:** `App` fetches clients and bookings, and shows loading and error states. A retry button reloads.
- **After a successful create:** show the confirmation from the API's response, then refresh bookings and clients, since a new client or dog may now exist.
- **After a successful cancel:** refresh bookings.

### Booking form

| Today | New |
|---|---|
| Owner free text | Client picker: suggests existing clients as you type (name, with phone if on file). Picking one sends `client: { id }`. A new name sends `client: { name, phone }` and shows an optional Phone field |
| Dog free text | Dog picker: suggests the chosen client's dogs. Picking one sends `dog: { id }`; a new name sends `dog: { name }`. For a new client, dogs are always new |
| Notes per day | One Notes field for the booking (`notes`, trimmed; sent as `null` when blank) |
| Day rate / overnight rate | Unchanged inputs. Each stay sends `unitRate` = day rate if drop-off and pick-up are the same date, otherwise overnight rate |
| Pickup/drop-off tick box | Sends `pickupDropoffFee` 15.00 when ticked, else 0 |
| "Times TBD" tick box | Ticked: send `dropOffTime` and `pickUpTime` as `null`. Unticked: send both as `HH:mm` |
| Price preview | Still calculated in the browser for display; the server's price is the one that's saved and shown on confirmation |

**Duplicate-name warning** (approved 2026-10-31):
- **When it shows:** a typed new client name matches an existing client (ignoring case and extra spaces).
- **What it shows:** "{name} is already a client — use them?", with a button that picks that client.
- **It doesn't block:** submitting anyway still creates a new client, because two people can share a name.

Client-side checks stay for quick feedback (required fields, pick-up not before drop-off). The server is the authority.

### Phone input (`phone.ts`)

Converts what's typed before sending:
- Remove spaces, dashes and brackets.
- A leading `00` becomes `+`, and `+440` (from `+44 (0)…`) becomes `+44`.
- A leading `07` becomes `+447`. A leading `447` becomes `+447`.
- Anything already starting with `+` is kept as is.
- A UK mobile (`+447…`) must be exactly `+447` plus 9 digits.

If the result doesn't match that, or `^\+[1-9][0-9]{7,14}$` for other numbers, the field shows "Enter a UK mobile or international number" and nothing is sent.

### Errors from the API

- **400 with field errors:** each error is shown on its input. Paths map as follows:
  - `client`, `client.name`, `client.phone` → client picker / phone
  - `dog`, `dog.name` → dog picker
  - `notes` → notes
  - `stays[i].dropOffDate` / `dropOffTime` → day *i+1* drop-off
  - `stays[i].pickUpDate` / `pickUpTime` → day *i+1* pick-up
  - `stays[i].unitRate` → the rate field used by that day
  - `stays[i].pickupDropoffFee` → day *i+1* pickup/drop-off
  - `stays` → a message above the days

  Unmapped field errors are listed in a banner.
- **409 phone already on file:** shows "This number belongs to *{existingClient.name}*. Use that client?" with a button that switches the picker to that client. Nothing is sent until you submit the form again.
- **404, 500, network:** a banner with the problem's title. The form keeps everything you typed.

### Confirmation

- Shows the booking the API returned: client, dog, each day with its service and price, and the total.
- **WhatsApp button:** unchanged behaviour, with the message filled in.
- **Calendar link and `.ics` download:** one calendar event per day, as today. Each event's UID uses that day's stay id (`stay-{stayId}@dogsitting.app`), so a booking with several days gets a distinct UID per event.

### History

- One card per booking, newest first: client, dog, total, created date, and each day (dates, times or "time TBD", service, price).
- **Cancel button:** shows a confirm prompt, then calls `cancelBooking`, then refreshes.
- **Cancelled bookings** stay listed, greyed out with a "Cancelled" chip and no Cancel button.
- The tab label count shows confirmed bookings.

## Testing

### API (Part 1)

The existing suite is updated for `/api` paths. `OpenApiTest` is extended as described in 1b.

### Website

MSW handlers fake `/api/clients` and `/api/bookings`. Tests:

| Area | Cases |
|---|---|
| `phone.ts` | `07700 900123` gives `+447700900123`; `447…` gives `+447…`; `+1 415 555 0100` is kept; junk is rejected |
| `api/client.ts` | Parses a booking; turns a 400 into `fieldErrors`, a 409 into `existingClient`, and a network failure into status 0 |
| Pickers | Typing suggests matching clients; picking one sends `{id}`; a new name reveals Phone and sends `{name, phone}`; the dog list follows the chosen client |
| Request building | Day care uses the day rate; multi-night uses the overnight rate; the pickup tick box sends a 15.00 fee; TBD sends null times; days with times send `HH:mm` |
| Errors | A 400 `stays[1].pickUpDate` shows under day 2's pick-up; a 409 offers to switch client; a network error keeps the form filled |
| Confirmation | Shows the server's prices and total; each day's calendar UID uses its stay id |
| History | Renders cards with days; cancelled cards are greyed with no Cancel button; Cancel confirms then calls the API and refreshes |

`npm run typecheck`, `npm run lint`, `npm run build` and `npm test` must pass.

### Manual check

Run Postgres.app, the API (`cd api && ./mvnw spring-boot:run`) and the website (`cd web && npm run dev`). Then:
1. Create a booking with a new client and dog.
2. Create another booking for the same client, picking them from the list.
3. Check both bookings in History.
4. Cancel one.
5. Confirm the rows in DBeaver (dev database).

## Out of scope

- Hosting the API and a production database.
- Login (auth) and CORS. CORS isn't needed while Vite proxies.
- **Moving the bookings saved in the live site's browser storage into the database.** The owner has real data there, so this must be designed with hosting, before merging this branch.
- Marking paid, editing bookings, per-day cancel.
- Opening the client's WhatsApp chat directly.
- Blocked dates.
