# Go-live Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the API-backed website live on Vercel safely. The API gets an owner login (sessions stored in Postgres, SPA CSRF and a brute-force throttle) and a production profile, then runs on Cloud Run against a Neon database. Client data is backed up every night, encrypted, to a private London bucket.

**Architecture:**
- **Login:** Spring Security 7 with one in-memory owner account, built from `OWNER_USERNAME` / `OWNER_PASSWORD_HASH` (`DelegatingPasswordEncoder` format).
  - A JSON `POST /api/login` controller authenticates the owner, rotates the session id and CSRF token, and saves the `SecurityContext` in the HTTP session.
  - Spring Session JDBC stores that session in `spring_session` (created by Flyway `V2`).
  - Logout is Spring Security's `LogoutFilter` on `POST /api/logout`.
  - Any 401 or 403 from the filter chain is passed to Spring MVC's `HandlerExceptionResolver`, so `ApiExceptionHandler` returns the same `ProblemDetail` JSON as everywhere else.
  - CSRF uses `csrf.spa()` (cookie `XSRF-TOKEN`, header `X-XSRF-TOKEN`), plus a small filter that makes sure the cookie is always written.
- **Website:** checks `GET /api/me` on startup and shows a login page on 401. Any later 401 returns to the login page. `client.ts` copies the CSRF cookie into the header.
- **Hosting:** a multi-stage Dockerfile, deployed by a GitHub Actions workflow with Workload Identity Federation to Cloud Run (`europe-west2`, 0–1 instances). A `vercel.json` rewrite keeps the browser on one origin.
- **Backups:** a nightly workflow streams `pg_dump | age | gcloud storage cp` into a private bucket.

**Tech Stack:**
- **API:** Spring Boot 4.1.2 (Spring Framework 7.0.10, Spring Security 7.1.2, Spring Session 4.1.1), Java 21, PostgreSQL 18, Flyway 12.4.0, springdoc-openapi 3.2.0.
- **Website:** React 19, MUI 9, Vitest 4 + MSW 2.
- **Containers:** `maven:3.9.16-eclipse-temurin-21-noble` (build) and `eclipse-temurin:21.0.13_9-jre-noble` (runtime).
- **Actions:** `google-github-actions/auth@v3`, `google-github-actions/setup-gcloud@v3`; `actions/checkout@v4` and `actions/setup-java@v4`, as in the existing workflows.
- **Hosting:** Google Cloud Run, Artifact Registry, Secret Manager, Cloud Storage; Neon (free plan, PG 18, London); Vercel.
- **Owner tools:** `age` and `pg_dump` / `pg_restore` 18.

**Spec:** docs/superpowers/specs/2026-10-31-go-live-design.md

**Ground rules (from CLAUDE.md):**
- **Dependencies:** no new ones beyond the three approved for the API, under the Boot 4 names the owner confirms in Task 0. None for the website.
- **Commits and pushes:** no commit without the owner approving the message, and no push at all. Pushing is an owner step in the runbooks.
- **Credentials and data:**
  - Never read or print `db.dev.local`. Appending to it is allowed only on the owner's explicit request.
  - Never touch production credentials or data.
  - The coding agent never runs anything against Google Cloud, Neon, GitHub settings or Vercel. Those are OWNER tasks.
- **Local servers:** don't start servers other than the one temporary API on port **8081** in Task 4. Never touch port 8080 or any process you didn't start.

## Things to know before starting

- **Branch:** `feat/go-live` (branched from `feat/web-api`). Check with `git branch --show-current`. It isn't pushed yet, and stays unpushed until the owner's first-deploy step.
- **Run Maven from `api/`.** `application.yml` imports `../db.dev.local` relative to the working directory. Tests need Postgres.app running (database `dd_pet_care_test`). The current baseline is **112 API tests** and **63 website tests**. If your baseline differs, add the deltas below to your own numbers.
- **Boot 4 splits auto-configuration into modules, so the approved dependency names change** (checked against `spring-boot-dependencies-4.1.2.pom` and the module jars):
  - `spring-boot-starter-security` exists as approved. It brings `spring-boot-security` (the auto-configuration) and Spring Security 7.1.2.
  - **`spring-session-jdbc` alone doesn't work in Boot 4.** The auto-configuration (`JdbcSessionAutoConfiguration`, the `spring.session.*` properties and the cookie serializer wiring) lives in `spring-boot-session-jdbc`, which comes with **`spring-boot-starter-session-jdbc`**. That starter also brings `spring-session-jdbc` 4.1.1 and `spring-boot-starter-jdbc` (already used).
  - **`spring-security-test` alone is the library only.** The `@AutoConfigureMockMvc` integration (`SecurityMockMvcAutoConfiguration`, which applies `springSecurity()` to the test `MockMvc`) lives in `spring-boot-security-test`. It comes with **`spring-boot-starter-security-test`**, which brings `spring-security-test` 7.1.2. This matches the existing `*-test` starters (`webmvc-test`, `jdbc-test`, `flyway-test`).
  - `spring-boot-starter-session-jdbc-test` also exists, but it only bundles `starter-session-jdbc` + `starter-jdbc-test` + `starter-test`, which are already present. It isn't needed.
- **Spring Security 7 facts this plan relies on (checked with `javap` on the 7.1.2 jars):**
  - `CsrfConfigurer.spa()` exists. It sets `CookieCsrfTokenRepository.withHttpOnlyFalse()` and a `SpaCsrfTokenRequestHandler`, but the token stays **deferred**. Nothing writes the `XSRF-TOKEN` cookie until something reads the token, which is why `CsrfCookieFilter` exists.
  - `DaoAuthenticationProvider(UserDetailsService)` is the constructor to use. `UsernamePasswordAuthenticationToken.unauthenticated(…)`, `HttpStatusReturningLogoutSuccessHandler(HttpStatus)`, `CsrfAuthenticationStrategy(CsrfTokenRepository)`, `ChangeSessionIdAuthenticationStrategy`, `CompositeSessionAuthenticationStrategy(List)` and `PasswordEncoderFactories.createDelegatingPasswordEncoder()` all exist.
  - `requestMatchers(String...)` and `requestMatchers(HttpMethod, String...)` exist (path patterns; `AntPathRequestMatcher` is gone in 7).
  - Test side: `SecurityMockMvcRequestPostProcessors.user(String)`, `csrf()` (with `asHeader()` and `useInvalidToken()`) and `anonymous()` exist. In Spring Test 7, `MockMvcRequestBuilders.get/post/delete` return `MockHttpServletRequestBuilder`, whose `with(…)` and `cookie(…)` return the same type.
- **Spring Session 4.1.1 / Boot 4.1.2 facts:**
  - The PostgreSQL schema is `org/springframework/session/jdbc/schema-postgresql.sql` in `spring-session-jdbc-4.1.1.jar`.
  - `spring.session.jdbc.initialize-schema` defaults to `embedded`; we set `never`.
  - `spring.session.jdbc.cleanup-cron` defaults to **every minute**; we set hourly, so Neon's free compute can suspend.
  - `spring.session.timeout` sets the inactivity timeout.
  - The cookie comes from `server.servlet.session.cookie.*` (`name`, `http-only`, `secure`, `same-site`, `max-age`).
  - **Session writes use their own `REQUIRES_NEW` transaction** (`JdbcHttpSessionConfiguration.createTransactionTemplate`, propagation 3). A test that really logs in therefore commits a `spring_session` row even inside `DatabaseTest`'s rollback. Those tests run with `@Transactional(propagation = NOT_SUPPORTED)` and delete the rows in `@AfterEach`, like `CreateBookingRollbackTest`.
- **How existing tests keep passing (spec: "done once in `DatabaseTest`'s request helpers").**
  - `getJson`, `postJson` and `postEmpty` now go through a new `perform(…)` helper that adds `user("ddpetcare")` and `csrf()`.
  - The raw `mvc` field stays anonymous, so the new security tests use `mvc.perform(…)` directly.
  - One existing test calls `mvc.perform` itself (`SpringErrorsStillMappedTest`'s `DELETE`); it changes `mvc.perform(` to `perform(` (one line). See "Clarifications", item 9.
- **Never use spring-security-test's `csrf()` post-processor** (post-review): it permanently swaps the shared `CsrfFilter` repository for the cached context, so later responses stop setting `XSRF-TOKEN`. Tests send a real `XSRF-TOKEN` cookie plus a matching `X-XSRF-TOKEN` header instead (`DatabaseTest.CSRF_TOKEN`).
- **MockMvc tests count as a WAR deployment,** so Boot ignores `server.servlet.session.cookie.*` there. `SecurityConfig.sessionCookie` re-applies those properties (null-safe), so cookie assertions work in tests.
- **`user(…)` vs `@WithMockUser`.** A class-level `@WithMockUser` would also apply to the new login tests and hide the real session. The per-request `user()` post-processor keeps raw `mvc` calls truly anonymous.
- **Errors from the filter chain go through `ApiExceptionHandler`.** The entry point and access-denied handler call the `handlerExceptionResolver` bean, with `handler = null`. With no handler, `ExceptionHandlerExceptionResolver` still applies global `@RestControllerAdvice` methods, so 401, 403 and 429 are `application/problem+json` with `instance` filled in, like every other error. Inject the bean with `@Qualifier("handlerExceptionResolver")`, because `DefaultErrorAttributes` is a `HandlerExceptionResolver` too.
- **BCrypt only reads the first 72 bytes** (checking a login silently truncates; only `encode` rejects longer input). `LoginRequest.password` is capped at 72 characters to bound the input, and the runbook tells the owner to pick a production password of 20–40 plain ASCII characters.
- **The throttle is one in-memory bean shared by every test in a cached context.** Tests that fail logins on purpose call `throttle.recordSuccess()` (the same reset a successful login does) in `@AfterEach`.
- **Website quirks:**
  - jsdom keeps `document.cookie` for the test origin (`http://localhost:3000`), so tests set `XSRF-TOKEN` there and clear it after.
  - A 204 response has no body, so `client.ts` returns `undefined` for 204 instead of parsing JSON.
  - No jest-dom.
  - After closing a `Dialog`, wait until it's gone (see `web/CLAUDE.md`).
- **No Docker locally.** Docker, `gcloud`, `gh`, `age` and `jq` aren't installed on this machine, and installing them isn't part of this plan. The Dockerfile is first built by the deploy workflow; workflow YAML is syntax-checked with the system Ruby (`ruby -ryaml`).
- **Vercel's external rewrite timeout is 120 s** (raised from 30 s on 2025-05-08, all plans; [changelog](https://vercel.com/changelog/cdn-origin-timeout-increased-to-two-minutes)). That covers a 5–15 s Cloud Run cold start, and Cloud Run's own 60 s request timeout is lower anyway. No mitigation needed.
- **GitHub Actions cron timezones** (`timezone:` next to `cron:`) shipped in March 2026 ([changelog](https://github.blog/changelog/2026-03-26-github-actions-late-march-2026-updates)), so "02:00 UK time" is `cron: '0 2 * * *'` with `timezone: 'Europe/London'`.

## Clarifications of the spec

1. **Dependency names (owner decision needed, Task 0).** Approved: `spring-boot-starter-security`, `spring-session-jdbc` and `spring-security-test`. In Boot 4.1.2 the working equivalents are `spring-boot-starter-security`, **`spring-boot-starter-session-jdbc`** and **`spring-boot-starter-security-test`** (see "Things to know"). The plan uses those three. Don't add them until the owner confirms.
2. **"Dev profile".** There's no `dev` profile today: local runs use plain `application.yml`. "Dev profile" means that default config, which sets the cookie `secure: false` and leaves the docs on. `application-prod.yml` overrides both.
3. **Session cookie lifetime.** The spec gives the server-side timeout (30 days of inactivity) but no cookie `Max-Age`. Without one, `SESSION` is a browser-session cookie that disappears when the browser closes. The plan sets `max-age: 30d`, so phones and laptops stay logged in. Spring Session only rewrites the cookie when the session changes, so in practice the owner logs in again at most every 30 days.
4. **Logout without a session** returns 204 too (it's Spring Security's `LogoutFilter`, which is idempotent). It still needs a CSRF token like any `POST`.
5. **Throttle scope.** It's one global counter, as the spec words it, not per IP or per username. Only the owner's account can succeed, and IPs behind Vercel can be spoofed. The downside is that someone can lock the owner out for 15 minutes at a time; that's listed in "Known risks".
6. **Error titles.**
   - Wrong login: 401 "Invalid username or password".
   - Throttled: 429 "Too many attempts, try again later".
   - No session: 401 "Not logged in".
   - CSRF: 403 "Forbidden".
   - Each has a short `detail`. The website shows the title.
7. **Login body validation.** `username` and `password` are `@NotBlank`; the password is at most 72 characters and the username at most 100. A blank or oversized body is a 400 `ValidationProblem` and doesn't count towards the throttle. The login page also checks for empty fields before calling the API.
8. **`/api/login` and `/api/me` appear in the OpenAPI spec** (with operation ids `login` and `getMe`), so the website gets generated `LoginRequest` / `MeResponse` types. `/api/logout` isn't documented, because it's a filter rather than a controller. `MeResponse` is added to `OpenApiSchemaCustomizer.ALL_PROPERTIES_REQUIRED`, per `api/CLAUDE.md`.
9. **One existing test changes by one line.** `SpringErrorsStillMappedTest` calls `mvc.perform(delete(…))` directly; it now calls the authenticated `perform(…)` helper. Without that, CSRF would turn its expected 405 into a 403.
10. **`vercel.json` can't read Vercel project settings or environment variables.** Rewrite destinations are literal. Cloud Run URLs are deterministic (`https://ddpet-api-<PROJECT_NUMBER>.europe-west2.run.app`), so the file is committed with the placeholder `PROJECT_NUMBER`, and the owner fills in the real number in one small commit after the first deploy (go-live runbook, step 3). The project number isn't secret: the URL is public anyway.
11. **Vercel preview (spec Part 5, step 4).** The spec previews "`feat/web-api` with `feat/go-live` merged into it", but step 6 only merges after the temporary trigger is removed. Vercel builds a preview for every pushed branch, and `feat/go-live` already contains all of `feat/web-api`. So the check uses the **`feat/go-live` preview**, which is the same code. The PRs then follow step 6.
12. **IAM API.** Creating the Workload Identity pool and the service accounts needs `iam.googleapis.com`, which isn't in the spec's list of APIs. The runbook enables it too.
13. **Deployer role.** `--allow-unauthenticated` sets an IAM policy on the service, which `roles/run.developer` can't do. The deployer gets `roles/run.admin`, plus `artifactregistry.writer` on the repo and `iam.serviceAccountUser` on the runtime service account only.
14. **Deploy workflow tests.** `api-deploy.yml` reuses `api.yml` (which gains a `workflow_call` trigger) instead of copying its Postgres service set-up.
15. **Where the manual backup commands live.** The spec says "the backup runbook's commands". They are the "Take a backup by hand" section of `docs/runbooks/restore-backup.md`, next to the restore.
16. **Phone in the client picker.** The spec removes the Phone *field*. The picker still shows the phone of a client already on file. Production starts empty and nothing can add a phone now, so no change is made there.

-- Spring Session JDBC schema for PostgreSQL, copied verbatim from
-- org/springframework/session/jdbc/schema-postgresql.sql in spring-session-jdbc-4.1.1.jar
-- (the version managed by Spring Boot 4.1.2). Flyway owns these tables:
-- spring.session.jdbc.initialize-schema is never.
CREATE TABLE SPRING_SESSION (
	PRIMARY_ID CHAR(36) NOT NULL,
	SESSION_ID CHAR(36) NOT NULL,
	CREATION_TIME BIGINT NOT NULL,
	LAST_ACCESS_TIME BIGINT NOT NULL,
	MAX_INACTIVE_INTERVAL INT NOT NULL,
	EXPIRY_TIME BIGINT NOT NULL,
	PRINCIPAL_NAME VARCHAR(100),
	CONSTRAINT SPRING_SESSION_PK PRIMARY KEY (PRIMARY_ID)
);

CREATE UNIQUE INDEX SPRING_SESSION_IX1 ON SPRING_SESSION (SESSION_ID);
CREATE INDEX SPRING_SESSION_IX2 ON SPRING_SESSION (EXPIRY_TIME);
CREATE INDEX SPRING_SESSION_IX3 ON SPRING_SESSION (PRINCIPAL_NAME);

CREATE TABLE SPRING_SESSION_ATTRIBUTES (
	SESSION_PRIMARY_ID CHAR(36) NOT NULL,
	ATTRIBUTE_NAME VARCHAR(200) NOT NULL,
	ATTRIBUTE_BYTES BYTEA NOT NULL,
	CONSTRAINT SPRING_SESSION_ATTRIBUTES_PK PRIMARY KEY (SESSION_PRIMARY_ID, ATTRIBUTE_NAME),
	CONSTRAINT SPRING_SESSION_ATTRIBUTES_FK FOREIGN KEY (SESSION_PRIMARY_ID) REFERENCES SPRING_SESSION(PRIMARY_ID) ON DELETE CASCADE
);
```

package com.ddpetcare.api.auth;

import java.io.IOException;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.security.web.csrf.CsrfToken;
import org.springframework.web.filter.OncePerRequestFilter;

// csrf.spa() defers the token, so the XSRF-TOKEN cookie is only written once something reads it.
// Reading it on every request means the website always has a cookie to copy into X-XSRF-TOKEN.
final class CsrfCookieFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        CsrfToken token = (CsrfToken) request.getAttribute(CsrfToken.class.getName());
        if (token != null) {
            token.getToken();
        }
        chain.doFilter(request, response);
    }
}

package com.ddpetcare.api.auth;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.ArrayDeque;
import java.util.Deque;

import com.ddpetcare.api.error.LoginThrottledException;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;

// In memory, which is enough with at most one Cloud Run instance; a restart resets it (spec: accepted).
@Component
public class LoginThrottle {

    static final int MAX_FAILURES = 5;
    static final Duration WINDOW = Duration.ofMinutes(15);

    private final Clock clock;
    private final Deque<Instant> failures = new ArrayDeque<>();
    private Instant blockedUntil = Instant.MIN;

    @Autowired
    public LoginThrottle() {
        this(Clock.systemUTC());
    }

    LoginThrottle(Clock clock) {
        this.clock = clock;
    }

    public synchronized void checkAllowed() {
        if (clock.instant().isBefore(blockedUntil)) {
            throw new LoginThrottledException();
        }
    }

    public synchronized void recordFailure() {
        Instant now = clock.instant();
        failures.addLast(now);
        while (!failures.peekFirst().isAfter(now.minus(WINDOW))) {
            failures.removeFirst();
        }
        if (failures.size() >= MAX_FAILURES) {
            blockedUntil = now.plus(WINDOW);
            failures.clear();
        }
    }

    public synchronized void recordSuccess() {
        failures.clear();
        blockedUntil = Instant.MIN;
    }
}
```
(The `while` loop always stops: the entry just added is `now`, which is after `now - WINDOW`.)

const CSRF_COOKIE = 'XSRF-TOKEN='

function csrfToken(): string | null {
  const cookie = document.cookie.split('; ').find((c) => c.startsWith(CSRF_COOKIE))
  return cookie ? decodeURIComponent(cookie.slice(CSRF_COOKIE.length)) : null
}

function headersFor(init: { method?: string; body?: string }): Record<string, string> {
  const headers: Record<string, string> = { Accept: 'application/json' }
  if (init.body) headers['Content-Type'] = 'application/json'
  const token = init.method && init.method !== 'GET' ? csrfToken() : null
  if (token) headers['X-XSRF-TOKEN'] = token
  return headers
}

async function request<T>(path: string, init: { method?: string; body?: string } = {}): Promise<T> {
  let response: Response
  try {
    // An absolute URL, because Node's fetch (used by the tests) can't resolve a relative one.
    response = await fetch(new URL(path, window.location.origin), { ...init, headers: headersFor(init) })
  } catch {
    throw new ApiError(0, 'Could not reach the server')
  }
  if (!response.ok) throw await problemFrom(response)
  if (response.status === 204) return undefined as T
  try {
    return (await response.json()) as T
  } catch {
    throw new ApiError(response.status, 'Unexpected response from the server')
  }
}

        err.pickUp = 'Must be on or after drop-off'
      if (Object.keys(err).length) eErr[entry.id] = err
    })

    return { sErr, eErr }
  }

  function showApiError(err: ApiError) {
    if (err.status === 401) {
      onUnauthorized()
      return
    }
    if (err.status === 400 && err.fieldErrors.length) {
      const mapped = mapFieldErrors(err.fieldErrors, entries)
      setSharedErrors(mapped.shared)
      setEntryErrors(mapped.entries)
      setStaysError(mapped.stays)
      if (mapped.unmapped.length) setBanner({ title: err.title, lines: mapped.unmapped })
      return
    }
    setBanner({ title: err.title, lines: err.detail ? [err.detail] : [] })
  }

  const totalPrice = entries.reduce(
    (sum, e) => sum + (calcPrice(e.dropOff, e.pickUp, e.pickupDropoff, shared.dayRate, shared.overnightRate) ?? 0),
    0,
  )

  async function handleSubmit(ev: FormEvent<HTMLFormElement>) {
    ev.preventDefault()
    const { sErr, eErr } = validate()
    setSharedErrors(sErr)
    setEntryErrors(eErr)
    setStaysError(null)
    setBanner(null)
    if (!shared.client || !shared.dog || Object.keys(sErr).length || Object.keys(eErr).length) return

    setSubmitting(true)
    try {
      const booking = await createBooking(
        buildCreateRequest({
          client: shared.client,
          dog: shared.dog,
          notes: shared.notes,
          dayRate: Number(shared.dayRate),
          overnightRate: Number(shared.overnightRate),
          entries,
        }),
      )
      onCreated(booking)
    } catch (err) {
      if (!(err instanceof ApiError)) throw err
      showApiError(err)
    } finally {
      setSubmitting(false)
    }
  }

  return (
    <Box component="form" onSubmit={handleSubmit} noValidate>
      <Stack spacing={2.5}>
        <Stack direction={{ xs: 'column', sm: 'row' }} spacing={2}>
          <ClientPicker clients={clients} value={shared.client} onChange={setClient} error={sharedErrors.client} />
          <DogPicker
            dogs={shared.client?.kind === 'existing' ? shared.client.client.dogs : []}
            value={shared.dog}
            onChange={setDog}
            error={sharedErrors.dog}
          />
        </Stack>

        <TextField
          label="Notes"
          multiline
          rows={2}
          fullWidth
          value={shared.notes}
          onChange={setField('notes')}
          placeholder="Feeding instructions, medical needs…"
          error={!!sharedErrors.notes}
          helperText={sharedErrors.notes}
        />

        <Stack direction={{ xs: 'column', sm: 'row' }} spacing={2}>
          <TextField
            label="Day Rate"
            fullWidth
            value={shared.dayRate}
            onChange={setField('dayRate')}
            error={!!sharedErrors.dayRate}
            helperText={sharedErrors.dayRate}
          />
          <TextField
            label="Overnight Rate"
            fullWidth
            value={shared.overnightRate}
            onChange={setField('overnightRate')}
            error={!!sharedErrors.overnightRate}
            helperText={sharedErrors.overnightRate}
          />
        </Stack>

        {staysError && (
          <Typography variant="body2" color="error">
            {staysError}
          </Typography>
        )}

        <Stack spacing={2}>
          {entries.map((entry, idx) => (
            <BookingEntry
              key={entry.id}
              entry={entry}
              index={idx}
              onChange={(updated) => updateEntry(entry.id, updated)}
              onRemove={entries.length > 1 ? () => removeEntry(entry.id) : null}
              errors={entryErrors[entry.id] ?? {}}
              dayRate={shared.dayRate}
              overnightRate={shared.overnightRate}
            />
          ))}
        </Stack>

        <Button variant="outlined" startIcon={<AddIcon />} onClick={addEntry} sx={{ alignSelf: 'flex-start' }}>
          Add another day
        </Button>

        {entries.length > 1 && totalPrice > 0 && (
          <>
            <Divider />
            <Stack direction="row" sx={{ justifyContent: 'space-between', alignItems: 'center' }}>
              <Typography variant="body2" color="text.secondary">
                Total ({entries.length} days)
              </Typography>
              <Typography variant="h6" color="primary" sx={{ fontWeight: 700 }}>
                £{totalPrice.toFixed(2)}
              </Typography>
            </Stack>
          </>
        )}

        {banner && (
          <Alert severity="error">
            <AlertTitle>{banner.title}</AlertTitle>
            {banner.lines.map((line) => (
              <Box key={line}>{line}</Box>
            ))}
          </Alert>
        )}

        <Button
          type="submit"
          variant="contained"
          size="large"
          startIcon={<PetsIcon />}
          disabled={submitting}
          sx={{ py: 1.5, borderRadius: 2, fontWeight: 700 }}
        >
          Create Booking
        </Button>
      </Stack>
    </Box>
  )
}

## Known risks

- **Dependency names.** The plan depends on the owner accepting `spring-boot-starter-session-jdbc` and `spring-boot-starter-security-test` (Task 0).
  - With plain `spring-session-jdbc`, Boot 4 configures nothing, so sessions would need hand-written `@EnableJdbcHttpSession` configuration.
  - With plain `spring-security-test`, the `user()` and `csrf()` post-processors probably still work, because Boot's MockMvc adds the security filter, but that's unverified.
- **Filter-chain errors through `HandlerExceptionResolver`.** If the resolver doesn't handle an exception, it returns `null` and the response is an empty 200. `AccessRulesTest` and `LoginTest` assert status, content type and title on every security path, so a regression shows up there.
- **Deferred CSRF cookie.** The website relies on `CsrfCookieFilter` writing `XSRF-TOKEN` on every response. After login, `CsrfAuthenticationStrategy` clears the old cookie, and the next request gets a new one.
  - The website always makes a GET after login (the lists), so its first POST has a token.
  - A POST sent straight after login with no GET in between would get a 403.
- **Logout failure.** If `POST /api/logout` fails (network, or a missing CSRF cookie), the website still shows the login page, but the server session stays valid until it expires or the owner logs out again.
- **Stored sessions and upgrades.** Spring Session stores the `SecurityContext` as Java-serialised bytes. After a Spring Security upgrade, old rows may fail to load, which can cause errors until `DELETE FROM spring_session;` is run. This is documented in `api/CLAUDE.md`.
- **Throttle.**
  - It's global and in memory, so anyone can lock the owner out for 15 minutes at a time by failing 5 logins (spec: accepted).
  - A restart or scale-to-zero resets the count; continuous attack traffic keeps the instance warm, so the count holds while it matters.
- **Cookie lifetime (Clarification 3).** The cookie expires 30 days after login, even with daily use; the server-side timeout is 30 days idle. `LoginTest` asserts `Max-Age`. If Boot 4.1.2 turns out not to map `server.servlet.session.cookie.max-age`, that assertion fails and the owner decides.
- **BCrypt 72-byte limit.** Passwords over 72 characters are rejected at login (400) and fail when hashing. The runbook says 20–40 characters.
- **Docker image never built locally.** There's no Docker on this machine. The first real build is in **api-deploy**.
  - `./mvnw` in the build stage downloads Maven 3.9.9 with `curl` or `wget`, both of which the Temurin-based Maven image should have. If the build fails there, replace `./mvnw` with `mvn` (the image's own Maven) and tell the owner.
  - The jar name in `COPY` is checked in Task 3 Step 5.
- **Memory.** 512 MiB with a 384 MiB heap (75%) should fit Spring Boot + Hibernate + Tomcat for one user. If Cloud Run logs show OOM kills, raise `--memory` to 1Gi; that may cost more.
- **Cold starts.**
  - The first request after idle takes about 5–15 s. Vercel waits up to 120 s and Cloud Run up to 60 s.
  - Startup CPU boost (`--cpu-boost`) could shorten it, but it isn't in the spec.
  - The website shows its loading spinner meanwhile.
- **Backup upload permissions.** `gcloud storage cp -` with only `roles/storage.objectCreator` is expected to work for new object names. If the first workflow run fails with a 403 on a `get` or `list`, don't grant read access to the bucket. Instead, grant a custom role with `storage.objects.create` plus the missing permission, and record it in `cloud-setup.md`.
- **The backup secret has write access.** `NEON_BACKUP_URL` uses the Neon owner role. A read-only Neon role for backups would be safer; that's a later hardening step.
- **Scheduled workflows.**
  - The `timezone:` key on cron schedules is new (March 2026). If GitHub rejects it, fall back to `cron: '0 2 * * *'` in UTC, which is 02:00 GMT in winter and 03:00 BST in summer.
  - GitHub may delay scheduled runs.
  - GitHub disables schedules in public repositories after 60 days without activity. A failed or missing run emails the owner; re-enable it in the Actions tab.
- **Costs.**
  - Cloud Storage's always-free 5 GB only covers US regions, so the London bucket costs pennies a month (30 days of small dumps).
  - Artifact Registry beyond 0.5 GB is billed, which the cleanup policy prevents.
  - Neon's free compute allowance assumes the database suspends when idle, which is why session cleanup is hourly. Cloud Run only gets CPU during requests, so idle instances barely run it.
- **Test data in production.** The preview check (step 4) creates real rows in Neon. The runbook makes their removal optional and owner-run.
- **Second Spring test context.** `ProdProfileTest` starts a second context, which cleans and migrates the test database again. That adds a few seconds to `./mvnw verify`.
- **springdoc and `@NotBlank`.** If springdoc doesn't mark `@NotBlank` fields as required, `LoginRequest.required` is set in `OpenApiSchemaCustomizer` instead (Task 1, Step 9).
- **CI before the first push.** Neither workflow has run yet. GitHub validates the workflow syntax, the `workflow_call` reuse and the WIF configuration on the first push of `feat/go-live` (go-live runbook, step 3).
